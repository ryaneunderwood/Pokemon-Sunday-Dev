[x] [2026-04-21] Wait for Move's Completion hang fixed — Interpreter#update
      now skips parallel-process events in the wait check so background
      auto-graphic events (e.g. Map 044 ev4 "crumbled" sprite selector)
      don't pin move_route_forcing true forever
  [2026-08-04] REPLACED. That fix worked but caused the lag and glitching Ryan
      reported. v21's command 210 is a map-wide barrier, and the old patch made
      it ignore every trigger-4 event - which also broke the ordinary idiom
      those same events use: force a route on self, wait for it, loop. Their
      wait then returned instantly, so ~10 ambient scenery events (Map174/179/
      193-200 and others) re-issued a move route every frame instead of every
      fifth. A harness modelling v21's interpreter measured 60 cycles per 60
      frames against a correct 12.
      Each interpreter now records what it force-routed and waits for exactly
      that, so scenery it never touched cannot block it and self-routing events
      still pace themselves. Interpreter#update is wrapped, not copied.
      The underlying event problem is unchanged and no longer matters: 17
      parallel pages force a route then loop with nothing pacing them.
  [2026-08-04] Map044 ev4 tidied up as well (tools/fix_map044_crumbled_event.rb):
      guarded by self switch A so the crumbled graphic is applied once instead
      of every frame forever. Safe only because the event has a single
      unconditional page - Game_Event#refresh returns early when the resolved
      page is already active, so the self switch cannot wipe the graphic the
      move route applied; a second page would have. Also restored the else
      branch that the v17 -> v21 port had turned into a nested
      "if character_ID == 2", which left any other character_ID with no
      graphic. The other 16 unpaced parallel pages are harmless now and were
      left alone.

[x] [2026-08-08] Save files from pre-port builds made unloadable by that shim
      removal — fixed. Deleting SundayIndexedStatHash broke Marshal.load on any
      existing save: the shim had been extend'd into each Pokemon's @iv/@ev
      Hash, and Marshal records extended modules by name in the stream, so
      loading raised "ArgumentError: undefined class/module SundayIndexedStatHash"
      in SaveData.get_data_from_file (StartGame:22).
      Fix: new plugin [008] Compatibility/[000] Save File Compatibility.rb
      redeclares SundayIndexedStatHash as an EMPTY module — enough for Marshal
      to resolve the name, with no method overrides, so the affected hashes
      behave as plain symbol-keyed Hashes. Confirmed safe: zero integer iv/ev
      subscripts remain in any Map*.rxdata or CommonEvents.rxdata.
      Verified by replaying the real save (AppData/Roaming/Pokemon Sunday 3.0/
      Game.rxdata, game_version 2.9.6) through Marshal.load with stand-ins for
      the RGSS/Essentials classes: the stream now resolves end to end, and
      SundayIndexedStatHash was the ONLY name in it not defined by stock v21.
      NOTE: this module must not be deleted — every save written before the
      2026-07-06 port depends on it existing.

      returns straight away. The plugin's own Options entry cannot rescue this
      either: its condition requires FollowingPkmn.get_event to be non-nil, so
      with no follower the toggle is hidden, and with the toggle hidden there is
      no way to make one.

      - follower_toggled defaults to true, written as a reader override rather
        than an initialiser so pre-existing saves pick it up (they have no
        @follower_toggled at all). Switching it off still sticks, false != nil.
      - The follower is seeded on :on_map_or_spriteset_change. add_follower only
        reads seven members off the event it is handed, so a Struct stand-in
        supplies them - the follower must exist on every map, not only one
        holding a seed event. Event ids start at 1 so id 0 cannot collide.
      - The Options entry is re-registered without the get_event condition, so
        the toggle is always visible, and switching it on creates the follower.
        MenuHandlers keys on the option symbol, so this replaces FPEX's row.
      Untested in game like everything else here.

EBDX BATTLE FIXES
-----------------
[x] Blank strip at the end of every trainer battle. pbShowOpponent slides the
      defeated trainer in by calling moveEntireScene(-6, -1) once per frame for
      20 frames, panning the whole camera 120px left and 20px up. Backdrops are
      384px wide - EBDX's own size, and all 52 custom ones match - so the pan
      runs off the end of the image.
      Fixed by EBDX's own switch: USE_TRAINER_OUT_OF_PLACE_HOTFIX false -> true
      in [003] Config/Config.rb. The pan is skipped and only the trainer sprite
      moves. Safe because pbShowOpponent and pbHideOpponent share the flag so
      they stay symmetrical, and because those two are the ONLY horizontal scene
      pans in the plugin - every other moveEntireScene call passes x = 0.
      Not a backdrop-size problem: 384x308 matches the 18 stock backdrops, the
      screen is the stock 512x384, and the VS bar is 768px wide.
[x] HP bar draining instantly. The step size was a red herring; the real fault
      is EbdxWaiter#wait, and it affected EVERY animation in the battle.
      The waiter keeps a running deadline: it adds its 0.025s tick to @timer_end
      and busy-waits "until System.uptime >= @timer_end", drawing a frame per
      pass. @timer_end is never clamped forward, so once real time overtakes it
      - after any slow stretch, a message box, a move animation, a stutter -
      every later wait adds 0.025s to a timestamp STILL in the past. The
      condition is already true, the body never runs, and wait returns having
      drawn nothing. is_too_stale? only resyncs after a full 2 seconds of
      deficit, leaving a wide window where every wait is a no-op. EBDX's author
      hit this: a commented-out echoln "We are overdue already!" sits on the
      line after the increment.
      The HP loop is "while animatingHP; update; wait(1); end", so the whole
      drain ran inside one rendered frame no matter how small each step was -
      which is why a first attempt at slowing the step down was invisible.
      Fixed in [001] Battle/[011] EBDX Sunday Tweaks.rb by clamping @timer_end
      forward to the present before delegating. EBDX loses the ability to catch
      up after a slow frame, which is the point: catching up here means dropping
      the animation instead of playing it.
      Blast radius is small - almost every other call site builds a fresh
      EbdxWaiter whose @timer_end starts at System.uptime and is already in
      sync, so the clamp is a no-op for them. Only the scene's long-lived
      singleton @waiter accumulates.
      The waiter clamp alone did NOT fix it. There is a second, independent way
      into the same state: Battle::Scene#wait only calls its waiter
      "if !EliteBattle.get(:smAnim)", and animateScene never calls
      Graphics.update itself, so while that flag is set wait draws nothing and
      returns at once. smAnim is a side effect of
      EliteBattle.sun_moon_transition?, which assigns @smAnim as it returns, so
      it can stay set outside the intro it was meant for. That guard is now
      removed - harmless here because sun_moon_transition? needs SM transition
      art under Graphics/EBDX/Transitions and this game ships none.
      The real lesson: the drain was never paced by how far the bar moves per
      update, but by how often update is called. Two attempts at shrinking the
      per-step change both failed, because a smaller step just meant more steps
      inside the same single rendered frame.
      The bar is now paced with System.uptime, so no wait-plumbing fault can
      compress it again. Duration scales with the fraction of the bar lost,
      HP_DRAIN_MIN 0.35s to HP_DRAIN_MAX 1.60s. Simulated at one step per 0.025s
      tick: half a bar 0.98s, full bar 1.60s, 1 HP chip 0.20s, and the same for
      300 HP losing 150 as for 100 losing 50. @currenthp stays an Integer
      because the databox prints it as text.
      WATCH FOR: other battle animations that were silently skipping frames will
      now play at their intended speed, so parts of the battle may feel slower.

[x] ALT game speedup rebuilt for v21. The port in "[014] v17 Field Systems.rb"
      section 6 copied v17's method - cycle Graphics.frame_rate through
      60/105/150 - which cannot work here. v17 counted frames, so a faster frame

      tone, flash, shake, picture moves, fog. The trade is that the trainer card
      no longer measures seconds at the wall; v17 chose the other way, hardcoding
      /40 in its load screen, but had no comparable-run-times reason to.

      frames (transitions, the Exp-full flash, window flashes).
